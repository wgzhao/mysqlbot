# 版本兼容架构：为什么是「信号登记表」而不是「按大版本切目录」

> 本文回答一个具体的设计问题：既然 5.7 / 8.0 / 8.4 的差异不小，
> 将来还要支持 9.x，规则库要不要改成「通用 + 按大版本特定」的目录结构？
>
> **结论：要的是「通用 + 特定」，但它已经在元数据层实现了，不需要切目录。**
> 真正缺的是把版本契约变成**可机检**的东西——那是本文描述的那一层。

---

## 一、先把问题量出来

讨论架构之前，先看仓库里的实际数字（2026-09-16）：

| 事实 | 数字 |
|---|---|
| 规则总数 | 42 |
| 声明 `@since: 5.7`（跨版本通用） | **38** |
| 声明 `@since: 8.0` / `8.0.13` | 3 / 1 |
| 真正需要**版本变体**的逻辑规则 | **2**（`blocking_chains`、`binlog_retention_unbounded`） |
| 触碰版本敏感信号的规则 | ~20（但其中 18 条用同一条 SQL 就兼容了） |

也就是说：**95% 的规则本来就是通用的，需要"特定"的只有 5%。**
为这 5% 把 42 个文件全部搬家，代价与收益不成比例。

再看"版本差异到底造成了多少麻烦"——按跳过原因分类（这是关键）：

| 环境 | 版本门禁跳过 | 权限/能力位跳过 | 执行失败 |
|---|---|---|---|
| Percona 5.7.44 | 4 | 0 | 0 |
| Percona 8.0.43（业务账号） | 2 | **9** | 0 |
| MySQL 8.4.11 | 2 | 0 | 0 |
| MySQL 9.7.2 | 2 | 0 | 0 |

**版本原因造成的跳过是少数，权限原因才是多数。**
而且版本门禁是**声明式**的（`@since` / `@removed_in`），一直工作得很好——
四个版本 0 报错。所以问题从来不是"路由不对"，而是"契约没人校验"。

---

## 二、为什么不按大版本切目录

设想 `rules/common/` + `rules/5.7/` + `rules/8.0/` + `rules/8.4/` + `rules/9.x/`：

**1. 版本维度与能力位维度是正交的。**
一条规则可以同时是 `@since: 8.0` **且** `@requires: p_s_locks`。
按版本切目录只能表达前者，于是路径会退化成 `rules/8.0/permission/...`——
既没回答"能不能在这版跑"，也没回答"这个账号能不能跑"。

**2. 覆盖空洞会变得不可见。**
现在两个变体在同一层 `ls` 里并排：

```
blocking_chains.sql        # 8.0+
blocking_chains_57.sql     # 5.7 ~ 8.0
```

一眼能看到对方。拆到两个目录之后，要发现"9.7 这个区间没有任何变体覆盖"，
得同时打开 `8.0/` 和 `9.x/` 对比。而**空洞的后果是规则静静地不跑**——
报告里它连"跳过"都不会出现，因为没有任何变体被选中执行。
目录结构上看不出任何异常（每个目录都"有东西"）。

**3. 改一条通用规则要动多处。**
38 条通用规则在 `common/`，但一旦某条需要变体，它要么被"搬出"通用目录，
要么在通用目录里留一份、在版本目录里再留一份。前者破坏"通用"目录的语义，
后者就是现在的 `_57` 后缀写法——只是换了个位置，还多了跨目录同步的负担。

**4. 目录回答不了真问题。**
"这套规则在 9.7 上能不能跑"是个**可计算**的问题，答案是元数据的函数，
和文件放在哪个目录毫无关系。把它做进目录结构，等于用摆放方式回答逻辑问题。

## 三、真正该做的：把版本契约变成可机检的

规则文件原本只有两样东西能表达版本兼容性：

- `@since` / `@removed_in` —— 整条规则的可用区间（粗粒度，靠人写）
- SQL 正文 —— 真正碰到的信号源（细粒度，但**没有人检查**）

两者之间**没有任何校验**。同一个事故于是反复发生：

> 一条规则写着 `@since: 5.7`，正文里却引用了 8.0.22 才有的列。
> 在 5.7 上执行抛 1054。修好之前，这个错误还会被错误分类降级成"跳过"，
> 报告里显示的是一句听上去很合理的"环境限制"。

**解法是补上第三样：一张"信号 → 可用版本区间"的登记表。**
实现见 `mbot/signals.py`，约 40 行常量。

```python
_var("expire_logs_days",       since="5.7", removed_in="8.4")
_var("binlog_expire_logs_seconds", since="8.0")
_tbl("performance_schema", "data_locks", since="8.0")
_tbl("information_schema", "INNODB_LOCK_WAITS", since="5.7", removed_in="8.0")
_col("events_statements_summary_by_digest", "QUERY_SAMPLE_TEXT", since="8.0.22")
```

### 3.1 硬引用 vs 软查表 —— 整个设计的关键

同一个信号，两种用法，后果完全不同：

```sql
-- 硬引用：变量不存在 → ERROR 1193，整条规则崩
SELECT @@binlog_expire_logs_auto_purge

-- 软查表：变量不存在 → 那行不存在 → MAX() 返回 NULL，规则自己兜住
SELECT MAX(CASE WHEN VARIABLE_NAME = 'binlog_expire_logs_auto_purge'
                THEN VARIABLE_VALUE END)
FROM performance_schema.global_variables
```

所以"这条规则的 `@since` 该写几"不能只看它碰了哪些信号，
还要看它是**怎么碰**的。`scan()` 返回的 `Usage` 带 `hard` 标记，
只有硬引用才构成版本依赖。这个区分让下面这条**不**误报：

```
innodb_redo_undersized   @since: 5.7
  软引用 innodb_redo_log_capacity(8.0.30) + innodb_log_files_in_group(5.7~8.4)
  → 变量缺失时那次 MAX() 返回 NULL，规则自动退回旧表达，无需变体
```

### 3.2 方向一：声明过宽（跨次版本 = 错误）

`lint` 静态比对"声明的区间"与"正文要求的最低版本"：

```
✗ metadata_lock_wait.sql: @since 5.7 过宽 —— 正文硬引用了
  performance_schema.metadata_locks（需要 5.7.3+）
```

跨次版本的差异是**错误**（规则会真的执行失败）；
只落在同一线内的补丁级差异是**提示**，因为生产上没人装 5.7.0~5.7.2，
报成错误只会淹没真问题。

这两个真发现（`metadata_locks` 5.7.3、`super_read_only` 5.7.8）**三个真实实例
永远测不出来**——我们手上的 5.7 都是 5.7.44。这正是登记表的价值：
它知道单台实例不可能告诉你的事。

### 3.3 方向二：该有上界却没声明

```
✗ x.sql: 硬引用了 variable:expire_logs_days（8.4 起移除），但没有声明 @removed_in
```

注意必须是**严格**比较：`@removed_in: 8.0` 与信号的 `removed_in: 8.0`
是同一个边界（都表示"8.0 起不可用"），边界相等是完美对齐，不是问题。

### 3.4 变体：从命名约定升级为声明

```sql
-- @id: blocking_chains_57
-- @variant_of: blocking_chains
```

`lint` 据此断言：**每个逻辑规则的变体集合必须无缝覆盖 `[5.7, +∞)`**——
没有空洞、没有重叠。当前两条逻辑规则都无缝覆盖：

```
blocking_chains:                blocking_chains [8.0~∞)  |  blocking_chains_57 [5.7~8.0)
binlog_retention_unbounded:     ...                      |  ..._57 [5.7~8.0)
```

这就是"按版本切目录"想解决、但其实解决不了的那个问题——
在平铺命名 + 显式区间下，空洞是可计算的。

## 四、离线推演：`mbot coverage`

```console
$ ./bin/mbot coverage --at 9.7
目标版本 MySQL 9.7  —— 纯静态推演，未连接实例
支持下界 5.7 · 参与推演 42 条规则

  预计运行       40
  版本门禁跳过    2   （区间不符，设计如此）
  版本风险        0   （硬引用的信号在这一版不存在，执行会失败）

门禁跳过：
  binlog_retention_unbounded_57      MySQL >= 8.0 已移除该信号源
  blocking_chains_57                 MySQL >= 8.0 已移除该信号源
```

`--matrix` 给出全版本网格：

```
规则                              5.7   8.0   8.4   9.0   9.7
binlog_retention_unbounded       ○     ●     ●     ●     ●
binlog_retention_unbounded_57    ●     ○     ○     ○     ○
blocking_chains                  ○     ●     ●     ●     ●
metadata_lock_wait               ●     ●     ●     ●     ●
sql_require_primary_key_off      ○     ○     ●     ●     ●
  合计 5.7: ●38 ○4 ✗0   8.0: ●40 ○2 ✗0   8.4: ●40 ○2 ✗0   9.0: ●40 ○2 ✗0   9.7: ●40 ○2 ✗0
```

**注意 `8.4 / 9.0 / 9.7` 三列全是 `✗0`。** 这不是巧合，是软查表写法的回报：
`expire_logs_days`、`innodb_log_file_size`、`innodb_log_files_in_group`
这三个在 8.4 被移除的变量，规则读它们的方式都是软查表，
所以 8.4 之后的移除**不需要改一行 SQL**。

其中 **9.7 这一列已经从"无已知风险"升级为"实测验证过"**（2026-09-16）：

| | 结果 |
|---|---|
| 端到端回归（种 17 处违规） | 42 条 · 命中 19 · 干净 21 · 跳过 2 · **失败 0**；17 条硬断言全中 |
| 推演对账 | 门禁 预测 2 / 实测 2 ✓　版本风险 预测 0 / 实测失败 0 ✓ |
| 与 8.4.11 对比 | **逐项相同**，而规则一行没改 |

也就是说 9.1 对 `performance_schema.data_locks` / `data_lock_waits` 的重设计，
实测**没有改变列集**，`blocking_chains` 照常跑通并命中。
`9.0` 那一列仍是推演值（没有 9.0 实例，且 9.0 不是 LTS）。

### 一个必须讲清的语义

`--at 5.7` 里的"5.7"补成 **5.7.999**，不是 5.7.0。

因为"这库跑在 5.7 上"在现实里指的是 5.7.3x~5.7.44，不是 2015 年的 5.7.0。
若补 0，一条 `@since: 5.7.3` 的规则会被判成"在 5.7 上不可用"，
而它在真实的 5.7.44 上跑得好好的——**推演结果会比现实更悲观，也就是在说谎。**
要严格按某个补丁判定，把版本写全：`--at 5.7.0`。

## 五、反馈回路：让现实纠正登记表

登记表是人写的，会过期。所以 `tests/live_compat.sh` 在跑完真实实例后，
**把离线预测和实测结果对账**：

```console
$ tests/live_compat.sh --defaults-file /tmp/mbot8040.cnf --label '8.0.43 (Percona)'
  目标版本 : 8.0.43-34  （推演按 8.0.43）
  门禁跳过 : 预测  2 / 实测  2
  版本风险 : 预测  0 / 实测失败  0
  软跳过   : 实测  9（权限/能力位/时长，离线不可知）

  ✓ 离线推演与实测完全吻合
```

对账靠的是**结构化的 `skip_kind`**，不是匹配中文 reason：

| `skip_kind` | 含义 | 对账时怎么用 |
|---|---|---|
| `version` | `@since`/`@removed_in` 门禁 | 必须等于预测的门禁集合 |
| `uptime` | 运行时长不足 | 离线不可知，不算不一致 |
| `capability` | 缺能力位（账号权限） | 离线不可知 |
| `permission` | 运行时被拒（1142 等） | 离线不可知 |
| `missing_object` | 运行时对象不存在 | **登记表该更新了** |

`missing_object` 这一行是重点。曾经这里靠字符串匹配
（`"需要 MySQL" in reason`），于是
`执行被拒（Table 'x' doesn't exist）`被归进了"权限跳过"，
对账给出一个**假的 ✓ 一致**——和当初那个假的"0 报错"是同一类错误。

反向验证（引用一张 9.0 才有的表，而登记表里没有它）：

```console
✗ 抓到 1 条「对象不存在」：['ref_9_0_table']
   => 登记表没有这个信号，请补进 mbot/signals.py 的 _ORDER
```

### 5.1 对账的盲区：软查表缺变量是**哑的**

上面这条回路只能抓到**硬引用**——硬引用缺变量会抛 1193，规则变成 `error`，对账才看得见。

而**软查表**缺变量时只是返回 NULL：规则既不报错、也不跳过，
可能**静静地给出错误结论**。这正是铁律 3 要防的那一类，也是登记表最后一个无人看守的角落。

补法是让 `mbot doctor` 连库时顺手把登记表里的 **21 个变量信号**逐条与实例对一遍
（存在性 + 区间预测），不一致就报 ✗ 并让自检失败：

```console
$ ./bin/mbot doctor --defaults-file /tmp/mbot97.cnf
...
信号登记表   : ✓ 21 个变量信号，实例存在 18 个，与登记区间吻合
```

反向验证（拿 5.7.44 去判定一台 9.7.2 实例）会抓到 8 条：

```console
✗ binlog_expire_logs_seconds：登记为 8.0 ~ 至今（区间外），实例上却仍存在
✗ expire_logs_days：登记为 5.7 ~ 8.4（区间内），实例上却不存在
✗ innodb_log_files_in_group：登记为 5.7 ~ 8.4（区间内），实例上却不存在
...
```

**为什么只对变量做**：表名与列名一律是硬引用（缺了报 1146/1054），
由 `error` 计数兜住；只有变量存在"软查表"这种哑失败。
少做一类无用功，也就少一类假阳性。

MariaDB 与早于 5.7 的版本会**显式跳过**并写出原因（登记表不覆盖它们），
不假装核对过——这同样是铁律 3。

`tests/live_compat.sh` 第一步就调 `doctor`，所以这条核对在所有目标实例上自动生效。

## 七、要加一个新版本（比如 9.x）时怎么做

按顺序，**第一步就能回答"要不要动代码"**：

1. **离线预判** —— `./bin/mbot coverage --at 9.7`
   如果 `版本风险 = 0`，说明现有规则不需要改（当前就是 0）。
2. **登记新信号**（如果有）—— 把该版本新增/移除的信号补进 `mbot/signals.py`
   的 `_ORDER`，并在 `docs/compat-matrix.md` 的实测表里记下依据。
   **登记表与实测表必须同源。**
3. **上真实实例** —— `tests/live_compat.sh --defaults-file ... --label '9.7'`
   这一步是**权威**。它会先跑 `doctor`（把登记表的变量信号与实例核对一遍），
   再把离线推演与实测结果对账。若对账报 `missing_object`、`实际失败但未预测到`，
   或 `doctor` 的 `信号登记表` 一行报 ✗，说明有信号没登记/登记错了，回到第 2 步。
4. **按需加变体** —— 只有差异是**结构性**的（列名/表存在性/字段语义变了）
   才加变体，并带 `@variant_of`。若只是版本自适应（某个变量在某版缺席），
   优先改写成软查表，不加变体。
5. **`./bin/mbot lint`** —— 断言变体集合无缝覆盖、声明与正文一致。

### 版本敏感信号：加变体还是改写？

判据很简单：

| 差异形态 | 做法 | 例子 |
|---|---|---|
| 变量在某版本缺席 | **软查表**，同一份 SQL | `innodb_redo_log_capacity` |
| 列名改了 | 只能用**低版本就有的列**，或加变体 | `LAST_SEEN_TRANSACTION` → `LAST_APPLIED_TRANSACTION` |
| 表换了一整套 | **加变体** | `INNODB_LOCK_WAITS` → `data_lock_waits` |
| 判定逻辑本身不同 | **加变体** | — |

## 八、已知局限（如实列出）

- **登记表只覆盖它登记过的东西。** 一个*新出现*的信号会被 `lint` 提示
  （"引用了未登记的对象"），但一个**同名但语义变了**的信号——
  例如 9.1 重新设计了 `performance_schema.data_locks` / `data_lock_waits`
  （为降低高并发下的 mutex 争用）——登记表看不出来。
  **只有真实实例能发现这类问题，所以步骤 3 不能省。**
- **`@since` 的下界是"声明"，不是"实测"。** 5.7.3 / 5.7.8 这类补丁级下界
  来自官方文档 + 单测，没有在那些版本的实例上真跑过（也拿不到）。
- `SUPPORTED_FROM = "5.7"` 是**政策**值，不是事实；
  实际有实例验证的最老版本是 5.7.44。
- **`9.0` 仍只是推演值**（非 LTS，没有实例）。`9.7.2` 已实测：端到端 42 条 0 报错、
  17 条硬断言全中、推演对账吻合，且规则一行未改。但请注意**这个结论的边界**：
  它证明的是"9.7.2 这一版能跑"，不等于"9.x 全线能跑"——
  9.1 那种跨次版本的重设计（`data_locks` / `data_lock_waits`）仍需逐版上实例验证。
